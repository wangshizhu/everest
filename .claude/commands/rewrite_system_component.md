# rewrite_system_component

## 输入

`$ARGUMENTS` — 系统组件名称，可以是中文名、英文名或源代码文件名。

- 为空时停止，并提示正确用法。
- 只给文件名时，按文件名、目录名、类名/宏名依次定位。
- 定位不唯一时列出候选，等待用户确认，不自行猜测。

## 范围与红线

- 搜索范围仅限 `everest/`。
- 本 skill 只做分析、review 和计划：不写实现代码、不写测试、不运行构建、不调用 `code-impl.ps1`。
- 不修改 `3rd/`。
- 不提交 commit，除非用户明确要求。
- 计划未经用户确认，不进入实现阶段。
- **禁止写无效信息**，无效信息反而是负担
- **极力将实现封装到cpp，对外隐藏实现，优先考虑封闭到cpp的方案**

## 必读规范

执行前完整读取以下文件；缺失时停止，不凭记忆：

- `doc/standard/code_standard.md`
- `doc/standard/cpp_style_guide.md`
- `doc/standard/review_standard.md`
- `doc/standard/refactor_standard.md`
- 仓库根 `CLAUDE.md`

## 步骤

### 1. 定位组件

- 优先按目录名、文件名匹配。
- 再按类名、宏名、关键函数名在 `everest/` 内 Grep。
- 输出候选项（文件、类、公共 API），必要时让用户确认。
- 确认组件边界：头文件、`.cpp`、`.ipp`、模板、宏、测试、示例。

### 2. 现状盘点

列出并确认：

- 组件包含的所有文件。
- 是否在统一编译单元 `everest/common/src/include.cpp` 中。
- 是否被 `everest/common/include.h` 收录。
- 被哪些其他组件依赖；公共 API 在 `test/` 和示例中的使用点。
- 当前编码、换行、缩进状态。
- 是否存在公共 API 变更需求；如有，列出所有调用方和迁移方式。

### 3. Review

按 `review_standard.md` 和 `code_standard.md` 通读组件，输出问题清单：

- 每条附 `file:line`、问题原因、影响、建议处理方式。
- 按 **阻塞 / 重要 / 建议** 分级。
- 重点检查：生命周期、线程安全、异步回调捕获、资源释放、边界条件、错误路径、日志、性能风险、迭代器失效、幂等性。
- 只报真实问题，不为 review 而 review。

### 4. 写计划

输出到 `doc/code-plan/<component>_plan.md`（目录不存在则创建）。

### 5. 等待确认

- 写完计划后停止，不写实现代码。
- 回复用户：计划路径 + 可直接复制的执行命令。
- 在用户明确确认之前，不进入实现。

## 计划文档

### 计划元信息（普通 Markdown 列表）

```markdown
## 计划元信息

- 组件名称：
- 组件边界：
- 目标平台：Windows / Linux
```

### 计划结构

```markdown
# <component> 重写计划

## 计划元信息

## 1. 目标与范围

## 2. 现状与依赖

## 3. Review 问题清单

## 4. 目标 API 与兼容性

## 5. C++20 特性使用

## 6. 文件改动清单

## 7. 构建与工程改动

## 8. 测试计划

## 9. 执行顺序

## 10. 风险与验收标准

## 11. 待确认项（按需）
```

### 内容要求

- 所有引用的现有函数、类、入口、常量都用 `file:line` 标注。
- 目标 API 给到签名、所有权、线程安全约定。
- 允许破坏性 API 变更，但必须列出新旧接口、迁移方式、影响范围。
- 文件改动清单区分新增、修改、删除、重命名。
- 构建改动明确 `include.cpp`、`include.h`、VS 工程、CMake、`.sln`。
- 测试计划使用 GoogleTest v1.14.0，列出测试文件、用例名、覆盖场景、预期结果、是否可自动运行。
- 测试计划必须分两类分别成表：
  - 正常路径：每个公共 API 的预期行为、返回值、状态变化。
  - 异常与边界路径：按目标 API 的真实错误出口逐条枚举——非法/空/越界/超限输入、错误码与 `Error()`/`Status` 契约、失败时状态不变、状态机非法调用（重入、重复 Start/Stop、关闭后使用）、生命周期风险、资源上限、并发与超时/断连。不写与本组件无关的通用条目。
- Review 问题清单中的每条 **阻塞 / 重要** 问题必须对应至少一条回归用例，用例表中标注对应的 review 编号；无法自动运行的（死亡测试、编译期 `static_assert`、需 sanitizer 的 UB）在“自动”列写“否”并说明原因。
- 执行顺序明确到文件和步骤。
- 不涉及的章节直接省略，不写“无 / 不涉及”。
- 计划末尾固定写明：
  - 本计划是待验证提案，不是规格；与规范冲突时以规范为准。
  - `file:line` 是写作时快照，执行前以当前代码为准。
  - 存在未决项时，`code-impl` 会停止询问。

## 输出

写完计划后只输出：

- 计划文档路径。
- 可直接复制的命令：

```text
/code-impl doc/code-plan/<component>_plan.md
```
